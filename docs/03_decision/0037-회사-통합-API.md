# ADR-0037. 회사 통합 API · 지원자 흡수 경로 4갈래로 · 코어는 API push 하나

> **상태**: 초안 · 2026-09-14 · 작성 suvisdev (인프라·총괄).
> 관련: [ADR-0033 지원자 앱 로그인](0033-지원자-앱-로그인.md) · [ADR-0035 헥사고날 부분 적용](0035-헥사고날-부분적용-Bounded-Context.md).

## 문제

Arda 가 채용 관리 시스템으로 자리 잡으려면 **회사가 이미 가진 이력서 접수 경로를 대체하는 게 아니라 흡수해야 한다.** 회사마다 상황이 다르다:

- 작은 회사: `careers@company.com` 메일로만 받고 있음.
- 중간 규모: 자체 커리어 페이지 · 폼 · DB 있음.
- 대형: Workday · SAP SuccessFactors 등 기존 ATS.
- 유입원이 잡보드 (사람인 · 잡코리아 · 원티드) 인 경우 다수.

경로가 다양한데 **접수 후 심사·면접·결정은 하나의 흐름** 이어야 한다 (Arda 코어). 흡수 경로별로 코드가 갈리면 유지 못 한다.

**"우리는 잡보드가 아니다"** — 지원자를 우리 도메인으로 몰아 유입원을 대체하는 게 목표가 아니다 (사용자 2026-09-14). Arda 는 채용 워크플로 · 심사 · AI 면접 이 상품이고, 접수 경로는 회사가 편한 방식을 그대로 쓰게 한다.

## 결정

**흡수 경로 4갈래를 정의하되, 코어는 회사 API push 하나로 통일**한다. 나머지 3 갈래는 API 위에 얹는다.

### 1. 흡수 경로 4갈래

| 경로 | 어떻게 들어오나 | 구현 위치 |
|---|---|---|
| **A. API Push** | 회사 백엔드가 Arda API 로 POST | 이 ADR 핵심 |
| **B. Widget/Embed** | 회사 커리어 페이지에 iframe·JS 위젯 | 프론트 · A 의 브라우저 래퍼 |
| **C. Email** | `apply@arda.io` 메일 파싱 → 내부 A 호출 | n8n · A 의 이메일 래퍼 |
| **D. Job Board Pull** | 잡보드 API → cron/webhook → A 호출 | 잡보드별 어댑터 · A 의 pull 래퍼 |

**B·C·D 는 A 의 래퍼**. A 하나만 잘 만들면 나머지 셋은 얇게 붙는다.

### 2. API 스펙 (POST `/api/v1/integrations/applications`)

**인증**: `Authorization: Bearer <company_api_key>` · 회사별 발급.

**요청 (예)**:
```json
{
  "external_id": "workday-app-abc-123",
  "posting_token": "arda-posting-xyz",
  "applicant": {
    "name": "홍길동",
    "email": "hong@example.com",
    "phone": "010-1234-5678",
    "birth_date": "19980315"
  },
  "resume": {
    "url": "https://company.com/files/abc.pdf"
  },
  "cover_letter": "저는 백엔드 개발자로서...",
  "source": "company_career_site"
}
```

- `external_id` — **회사 쪽 unique id.** 중복 요청 시 idempotent (같은 external_id 두 번 오면 기존 지원 반환).
- `posting_token` — Arda 공고 식별. 회사가 Arda 관리 UI 에서 확인.
- `applicant` — 필수 정보 4가지. 지원자 앱 로그인 (ADR-0033) 이 이메일 + 생년월일이라 그 두 개는 필수.
- `resume` — `url` (Arda 가 다운로드) 또는 `base64` (직접 포함). 둘 중 하나.
- `source` — 유입 채널 추적용.

**응답 201**:
```json
{
  "arda_application_id": 12345,
  "status": "received",
  "public_url": "https://seuk.suvisdev.cloud/my/12345"
}
```

**응답 200 (이미 있음 · idempotent)**:
- 같은 `external_id` 로 두 번 오면 최초 응답과 동일한 body · status 200.

**오류**:
- 401 · API key 없음/잘못됨
- 404 · `posting_token` 없음
- 422 · 필수 필드 누락 · 이메일 형식 · birth_date 형식
- 502 · resume url 다운로드 실패

### 3. DB 스키마

**신규 테이블 `integration_clients`**:
```sql
CREATE TABLE integration_clients (
  id SERIAL PRIMARY KEY,
  company_id INT REFERENCES company_profiles(id),  -- 회사 하나에 여러 key 가능 (rotation)
  api_key_hash TEXT NOT NULL UNIQUE,               -- bcrypt(api_key)
  api_key_prefix TEXT NOT NULL,                    -- key 앞 8글자 (관리 UI 표시용)
  name TEXT NOT NULL,                              -- "Workday integration" 등 별칭
  webhook_url TEXT,                                -- (선택) 상태 변경 시 콜백
  webhook_secret TEXT,                             -- 콜백 HMAC 서명 비밀
  rate_limit_per_minute INT DEFAULT 60,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  revoked_at TIMESTAMPTZ,                          -- soft delete (감사 · 최근 사용 확인)
  last_used_at TIMESTAMPTZ                         -- 최근 요청 시각
);
CREATE INDEX ON integration_clients(company_id);
CREATE INDEX ON integration_clients(api_key_hash) WHERE revoked_at IS NULL;
```

**`applications` 테이블에 컬럼 추가**:
- `external_id TEXT` (nullable · idempotency 키)
- `integration_client_id INT REFERENCES integration_clients(id)` (nullable · 어떤 통합으로 왔는지)
- `source TEXT` (자유 문자열 · "workday" · "email" · "saramin" · "direct" 등)

UNIQUE constraint: `(integration_client_id, external_id)` — 같은 통합에서 같은 id 두 번 못 옴.

### 4. 이력서 다운로드

`resume.url` 이 오면 **백엔드가 서명된 요청으로 그 URL 다운로드** → 우리 S3 저장.

- **동기 vs 비동기**: 응답 지연 방지 위해 **API 응답은 즉시 반환하고 다운로드는 백그라운드**. n8n 워크플로 or 비동기 task queue.
- **크기 제한**: 10MB (F3 파일 검증 규칙 상속).
- **MIME 확인**: `application/pdf` · `application/vnd.openxmlformats-officedocument.wordprocessingml.document` (docx) · `application/x-hwp` 만.
- **다운로드 실패 시**: 지원자에게 메일로 "이력서 재업로드 링크" 전송 (ADR-0033 로그인 기반).

`resume.base64` 는 API 응답 전에 즉시 저장 (다운로드 없음).

### 5. 인증 · 보안

- API key = 256-bit URL-safe token · bcrypt 해시로 저장.
- 관리 UI 에서 발급 시 **한 번만** 표시. 이후 프리픽스 (`arda_ak_abc12345...`) 로만 식별.
- Rate limit: 회사당 60 req/min (조정 가능).
- Idempotency 키: `external_id` 로 24h 캐시 · 재요청 시 원 응답 반환.
- Webhook: HMAC-SHA256 서명 (`webhook_secret`) 으로 회사가 무결성 검증.

### 6. B·C·D 는 A 의 래퍼

**B. Widget/Embed** (프론트):
- 브라우저에서 폼 렌더 → 지원자가 입력 → 그 데이터를 **A API 로 내부 호출** (임의 company_api_key 는 위젯이 안 씀 · 대신 `posting_token` 만으로 접근 가능한 공개 흐름 필요 · 다음 단락 참고).

**C. Email**:
- SES 수신 → n8n 파싱 → **A API 호출**.
- `apply@arda.io` 는 우리 도메인 · 회사별 별칭 (`apply+coA@arda.io`) 로 회사 판정.

**D. Job Board Pull**:
- 잡보드별 어댑터 (cron or webhook) → **A API 호출**.
- 잡보드마다 `source="saramin"` 등 기록.

**⚠️ 주의**: A API 는 회사 쪽 인증 (bearer token) 이 있어야 함. B (위젯) 는 브라우저 코드라 토큰 노출 위험. **B 는 별도 공개 엔드포인트** (`/public/apply/<posting_token>`) 를 A 안에서 재사용. 이건 이미 존재 (`app/application/api/public.py`).

### 7. 관리 UI (별도 세션)

관리자 화면 `/settings/integrations` 에서:
- API key 발급·회수 (뒤에서 한 번만 표시)
- 회사별 목록 (`name` · `api_key_prefix` · `last_used_at`)
- Webhook URL 설정
- 통계 (건수 · 성공률 · 최근 오류)

이 UI 는 이 ADR 범위 밖 · 후속 PR.

## 배제한 대안

**GraphQL API**: REST 하나 더 만들면 스키마 이중화. 회사 개발자 학습 곡선 +. 기각.

**gRPC**: 회사 시스템 (Workday · SAP) 은 대개 REST/HTTP 만 지원. 기각.

**Webhook only (Arda 가 회사로 pull)**: 회사가 API 제공해야 함 · 회사 개발 부담 큼 · 우리가 통제 못 함. Push 가 표준. 기각.

**공개 API key (회사 로그인 없이)**: 봇 남용 위험. 기각.

## Phase B 이력서 받기 — 구현 기록 (2026-09-17, woojeongalex)

위 §4 를 이렇게 구현했다. 코드는 `backend/app/application/resume_fetch.py`.

- **n8n 이 아니라 FastAPI `BackgroundTasks`.** 받은 파일은 S3·`files` 행·요약·앵커로 이어져야 하는데, 그 코드는 전부 백엔드에 있다. n8n 을 거치면 파일이 한 번 더 오가고 실패 지점이 하나 는다. 지원 폼의 요약·앵커와 같은 방식이다.
- **§4 「서명된 요청으로 다운로드」 대신 SSRF 차단을 본체로 했다.** 회사 키 하나로 서버가 임의 주소를 열게 되기 때문이다(EC2 메타데이터 `169.254.169.254` 등). http·https + 80·443 만, 이름을 풀어 **전부 공인 주소일 때만**, 확인한 IP 로 직접 연결(DNS rebinding 차단), 리다이렉트는 3회까지 매번 재검사.
- **형식은 바이트로 판정한다.** §4 의 MIME 목록은 상대 서버가 붙이는 값이라 믿지 않는다. 허용 목록은 지원 폼(F3)과 같은 pdf·docx·hwp·hwpx. `application/x-hwp` 만 적은 §4 와 달리 hwpx 도 받는다 — 폼과 같아야 한다.
- **받지 못하면 요약·자동 심사를 돌리지 않는다.** 이력서 없이 돌리면 [ADR-0034](0034-에이전트-자동심사.md) 가 우리의 내려받기 실패를 이유로 지원자를 떨어뜨릴 수 있다. 지원자에게는 안내 메일(`email_logs.stage='resume_missing'`, alembic 0025).
- **§4 「재업로드 링크」는 없다.** 지원자가 파일을 올릴 화면이 아직 없어서, 메일은 「처음 지원한 채용 페이지에서 다시 제출하거나 담당자에게 문의」로 안내한다. 대신 **회사가 같은 `external_id` 로 다시 보내면 그때 다시 받는다** — 이력서가 아직 없을 때만.
- **§2 의 「502 · resume url 다운로드 실패」는 없다.** 받기가 응답 뒤라 URL 실패는 응답에 안 실린다. 502 는 base64 를 우리 S3 에 못 올렸을 때만.
- **Phase A 에서 고친 것**: ① `/integrations/keys` 에 인증이 없었다(PR #280) ② base64 이력서를 S3 에 올리고 `files` 행을 안 만들어 담당자 화면에 이력서가 안 보였다 ③ 크기·형식 검사 없음 ④ 접수 이력(`stage_history`)·요약·앵커가 안 돌았다 — 통합으로 온 지원자는 자동 심사에 들어가지 못했다 ⑤ 같은 공고·같은 이메일 충돌이 DB 오류 문구와 함께 500 으로 나갔다 → 409.
